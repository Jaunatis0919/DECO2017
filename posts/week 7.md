## Part 1: From Pages to User Actions

In Week 7, I started to think less about separate pages and more about the user's emotional journey. The main flow is: create a burning post, wait or return to it, then choose Save it or Let it go. After that, the system should move the post into the correct space: Grave, Ash Field, or Community if the grave is made public.

This helped me see that the app needed a clear action path, not just navigation links. If the user creates a post but does not know where it goes next, the concept fails even if the database works.

## Part 2: Sitemap and Page Roles

The sitemap was organised around four main areas. Garden is the home space and contains the active burning posts. Grave stores saved memories. Ash Field shows released posts as dandelions. Community shows public graves and limited social interaction.

I decided that Garden should be the centre of the app because it contains the first and most important user action. Community should not be the first focus because the project is about private emotional expression before public sharing. Inbox and Profile can support the experience, but they are not the core of the prototype.

## Part 3: MVP and Future Scope

The MVP features are login, create burning post, save post, release post, view Grave, view Ash Field, and view public graves. These are enough to test whether the main concept makes sense.

Features such as real-time chat, complex friend systems, detailed notifications, or recommendation logic were moved into future scope. They could make the app richer, but they would also increase privacy risk and technical complexity. For this prototype, a smaller working emotional flow is more valuable than a large unfinished platform.

## Design Decisions

1. I placed Garden at the centre of the sitemap because it is where the user begins the emotional expression flow.
2. I separated Save it and Let it go into two clear outcomes because the app needs to support both preservation and release.

## Personal Reflection

This stage helped me understand that a web app flow should be judged by user decisions and system responses. The question was not only "what pages do we need?" but "what does the user do, and how does the system show that something has changed?"
